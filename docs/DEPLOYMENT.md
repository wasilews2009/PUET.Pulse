# PUET.Pulse: пробний запуск, тестування і розгортання в університеті

Документ для керівника проєкту та IT-центру ПУЕТ. Він має три частини:

1. [Пробний запуск на одному комп'ютері](#1-пробний-запуск-на-одному-компютері): щоб побачити месенджер за 30–40 хвилин.
2. [Тестування](#2-тестування): автоматичні тести і сценарії ручної перевірки.
3. [Розгортання в університеті](#3-розгортання-в-університеті): сервери, SSO, дзвінки, TLS, резервні копії, пілот.

Як користуватися самим месенджером, описано в [USER_GUIDE.md](USER_GUIDE.md).

---

## 1. Пробний запуск на одному комп'ютері

Пробний стенд має все справжнє: вхід через Keycloak з двофакторною
автентифікацією, базу PostgreSQL, сховище файлів, антивірус. Люди в ньому
вигадані, а Keycloak працює в режимі розробки. Тому використовуйте стенд лише
для знайомства й демонстрацій, а не для реальних даних.

### Що потрібно

- Linux або macOS (на Windows підійде WSL 2), 8 ГБ пам'яті, 15 ГБ диска.
- Docker з Docker Compose v2.
- Node.js 22 і pnpm 10: `corepack enable`.
- Браузер Chrome, Edge або Firefox.

### Кроки

```bash
git clone https://github.com/wasilews2009/PUET.Pulse.git && cd PUET.Pulse
git checkout claude/project-thread-l63ox0        # до злиття PR #1

cp infra/demo.env.example .env                   # готові налаштування для пробного стенда
docker compose --profile demo up -d              # PostgreSQL, Redis, MinIO, ClamAV, демо-Keycloak
pnpm install
pnpm build
pnpm db:deploy                                   # створює таблиці
pnpm db:seed                                     # структура ПУЕТ: тенанти, інститути, кафедри, служби
pnpm start:api                                   # API на :3000, залиште це вікно відкритим
```

У другому вікні терміналу:

```bash
pnpm demo:data                                   # тестові люди, група і курс (через підписану синхронізацію)
pnpm admin:bootstrap DEMO-ADMIN                  # перший адміністратор системи
pnpm --filter @puet/web dev                      # веб-клієнт на http://localhost:5173
```

ClamAV при першому запуску завантажує антивірусні бази, це триває до 5 хвилин.
Поки бази не готові, завантажені файли чекають у карантині й з'являються
пізніше.

### Вхід

Відкрийте http://localhost:5173 і натисніть «Увійти через корпоративний SSO».

| Логін | Хто це | Що показує |
|---|---|---|
| `student` | Андрій Пробний, староста групи DEMO-KN-21 | чати групи й курсу, сервіси, анонімні звернення |
| `student2` | Марія Зразкова, студентка тієї ж групи | листування між студентами, E2EE-чати |
| `minor` | Софія Юна, 16 років | захист неповнолітніх: фільтр лексики й посилань, обмежений довідник |
| `lecturer` | Олена Демченко, доцент кафедри КН та ІТ | курс «Вебтехнології (демо)», гілки, консультації, опитування |
| `ombudsman` | Ігор Тестовий, офіс омбудсмена | отримує анонімні звернення (потрібен TOTP) |
| `admin` | Демо Адміністратор | панель адміністрування (потрібен TOTP) |

Початковий пароль для всіх: `Pulse-demo-2026`. Keycloak одразу попросить
змінити його. Для `admin` і `ombudsman` Keycloak також попросить налаштувати
двофакторну автентифікацію: відскануйте QR-код застосунком Google
Authenticator, Microsoft Authenticator або FreeOTP. Під час першого входу ці
двоє бачать форму входу двічі. Це нормально: месенджер просить підтвердити
вхід другим фактором.

Щоб бачити двох людей одночасно, відкрийте другий браузер або вікно в режимі
інкогніто.

### Зупинка і повне скидання стенда

```bash
docker compose --profile demo down               # зупинити, дані залишаються
docker compose --profile demo down -v            # зупинити і видалити всі дані стенда
```

Після видалення даних повторіть кроки з `pnpm db:deploy`. Якщо ви
перестворили лише Keycloak, вхід за старими обліковими записами відмовить:
месенджер пам'ятає, до якого облікового запису Keycloak прив'язана людина.
Найпростіше видалити всі дані стенда і почати знову.

## 2. Тестування

### Автоматичні тести

```bash
pnpm typecheck                                   # перевірка типів у всіх пакетах
pnpm test                                        # модульні тести
RUN_DB_TESTS=1 DATABASE_URL=postgresql://... pnpm test   # плюс наскрізні тести на PostgreSQL
```

Для наскрізних тестів потрібна окрема порожня база після `pnpm db:deploy` і
`pnpm db:seed`. Не запускайте їх на робочій базі. GitHub Actions виконує все це
для кожного коміту (`.github/workflows`).

Зараз проходять: API 195 тестів, правила доступу 91, веб-клієнт 44, E2EE 10,
десктоп 5. Безпекові тести названі за атакою, від якої захищають: IDOR, XSS,
CSRF, open redirect, ізоляція неповнолітніх, підробка підпису тощо.

### Ручна перевірка на пробному стенді

Пройдіть ці сценарії перед пілотом. Кожен займає кілька хвилин.

| № | Сценарій | Очікуваний результат |
|---|---|---|
| 1 | `student` пише в чат групи DEMO-KN-21, `student2` читає | повідомлення приходить миттєво |
| 2 | `lecturer` пише в курсі «Вебтехнології (демо)», `student` відповідає в гілці | студент не може писати нове повідомлення верхнього рівня, лише в гілці |
| 3 | `student` створює особистий чат з `student2` і вмикає «Зникаючі повідомлення» | повідомлення наскрізно зашифровані, зникають після обраного часу |
| 4 | `student` завантажує PDF у чат групи | файл спершу в карантині, після перевірки ClamAV відкривається у захищеному переглядачі |
| 5 | Завантажте тестовий «вірус» EICAR (eicar.org) | файл відхилено, у чат він не потрапляє |
| 6 | `minor` пише нецензурне слово або посилання на сторонній сайт | повідомлення не надсилається, пояснення українською |
| 7 | `minor` шукає людей у довіднику; `admin` шукає `minor` | неповнолітня бачить лише свою групу й працівників; її бачать лише одногрупники та працівники |
| 8 | `student` → «Сервіси» → «Анонімне звернення» → омбудсмен | `ombudsman` бачить звернення від псевдоніма, без імені студента |
| 9 | `admin` → «Адміністрування» → «Симулятор доступу» | можна перевірити, чи дозволена дія конкретній людині, і чому |
| 10 | `admin` → «Журнал аудиту» → «Перевірити ланцюжок хешів» | ланцюжок цілий; відмови й чутливі дії записані |
| 11 | `lecturer` створює сертифікат УЕП у «Налаштуваннях» і підписує PDF | на файлі з'являється «Підписано ЕП», QR веде на сторінку перевірки (потрібен внутрішній ЦСК: `pnpm pki:init-ca`) |
| 12 | `lecturer` вмикає «На парі», `student` пише йому | сповіщення затримується до кінця статусу |

Знайдені проблеми записуйте із зазначенням логіна, часу і кроків. Не
надсилайте паролі, коди TOTP чи вміст особистих повідомлень.

## 3. Розгортання в університеті

### 3.1. Схема

```
Користувачі ──HTTPS (TLS 1.3)──> nginx ──> API (Node.js 22) ──> PostgreSQL, Redis, MinIO, ClamAV
                                   │                 │
                                   │                 ├──> Keycloak (SSO) ──> AD / LDAP
                                   │                 └──> вебхуки ЄДЕБО, HR, ERP, Деканат, ЕДО
                                   └──> LiveKit (дзвінки, wss + UDP)
```

Сервіси даних слухають лише `127.0.0.1` або внутрішню мережу. Назовні відкриті
тільки nginx (443) і медіапорти LiveKit.

### 3.2. Сервери

Оцінка для університету до 15 тисяч облікових записів і до 2 тисяч людей
одночасно. Уточніть її під час пілоту за реальним навантаженням.

| Сервер | Ресурси | Що на ньому |
|---|---|---|
| Застосунок | 4 vCPU, 8 ГБ RAM, 50 ГБ SSD | nginx, API, веб-клієнт |
| Дані | 4 vCPU, 16 ГБ RAM, 200 ГБ SSD + сховище файлів від 1 ТБ | PostgreSQL 16, Redis 7, MinIO, ClamAV |
| Дзвінки | 8 vCPU, 8 ГБ RAM, канал від 1 Гбіт/с | LiveKit |
| SSO | 2 vCPU, 4 ГБ RAM | Keycloak (якщо в університеті його ще немає) |

ОС: Ubuntu Server 24.04 LTS або Debian 12. На пілоті сервери застосунку й
даних можна об'єднати.

Доменні імена (приклад): `pulse.puet.edu.ua` (месенджер),
`sso.puet.edu.ua` (Keycloak), `meet.pulse.puet.edu.ua` (дзвінки).

### 3.3. Встановлення

1. **Сервер даних.** Встановіть Docker, скопіюйте репозиторій і запустіть
   інфраструктуру без демо-профілю:
   ```bash
   cp .env.example .env           # замініть усі CHANGE_ME (див. 3.4)
   docker compose up -d           # PostgreSQL, Redis, MinIO, ClamAV
   ```
   Для MinIO у продакшені замість статичного ключа `MINIO_KMS_SECRET_KEY`
   рекомендується MinIO KES з Vault або HSM.

2. **Сервер застосунку.** Встановіть Node.js 22 і pnpm, зберіть проєкт:
   ```bash
   sudo useradd --system --home /srv/puet-pulse puet-pulse
   sudo git clone https://github.com/wasilews2009/PUET.Pulse.git /srv/puet-pulse/app
   cd /srv/puet-pulse/app && pnpm install --frozen-lockfile && pnpm build
   sudo install -m 600 .env /etc/puet/pulse.env      # налаштування, лише для root
   PULSE_ENV_FILE=/etc/puet/pulse.env pnpm db:deploy
   PULSE_ENV_FILE=/etc/puet/pulse.env pnpm db:seed
   ```

3. **Внутрішній ЦСК (УЕП).** Один раз, ключ зберігається поза репозиторієм:
   ```bash
   sudo -u puet-pulse PULSE_ENV_FILE=/etc/puet/pulse.env pnpm pki:init-ca /etc/puet/ca
   ```
   Зробіть офлайн-копію `ca.key.pem` (зашифрована флешка в сейфі). Для
   продакшену розгляньте апаратний модуль (HSM).

4. **API як служба.** Приклад: `infra/systemd/puet-pulse-api.service`.
   ```bash
   sudo cp infra/systemd/puet-pulse-api.service /etc/systemd/system/
   sudo systemctl daemon-reload && sudo systemctl enable --now puet-pulse-api
   curl -s http://127.0.0.1:3000/health           # {"status":"ok",...}
   ```

5. **Веб-клієнт і nginx.** Скопіюйте `apps/web/dist` у `/srv/puet-pulse/web` і
   візьміть за основу `infra/nginx/pulse.conf` (TLS 1.3, HSTS, суворий CSP,
   проксі `/api` і `/api/ws`). Сертифікат TLS видає університет або
   Let's Encrypt. Перевірка: https://www.ssllabs.com/ssltest/ має показати A+.

6. **Перший адміністратор.** Після першої синхронізації з HR (3.6):
   ```bash
   PULSE_ENV_FILE=/etc/puet/pulse.env pnpm admin:bootstrap <службовий ID>
   ```
   Скрипт працює лише один раз, поки в системі немає жодного `SUPER_ADMIN`.
   Наступних адміністраторів призначають у панелі адміністрування.

7. **Десктопні й мобільні застосунки.** Див. `apps/desktop/README.md`.

### 3.4. Налаштування (`/etc/puet/pulse.env`)

Повний перелік з поясненнями наведено в `.env.example`. Секрети генеруйте так:
`openssl rand -hex 32`. Не використовуйте один секрет двічі.

| Змінна | Що це |
|---|---|
| `NODE_ENV=production` | вмикає захищені cookie і суворі перевірки |
| `DATABASE_URL`, `REDIS_URL` | адреси бази й Redis з паролями |
| `S3_*`, `MINIO_*` | сховище файлів; `S3_ACCESS_KEY_ID` — окремий обліковий запис API, створюється автоматично |
| `WEB_ORIGIN=https://pulse.puet.edu.ua` | адреса месенджера (захист від CSRF) |
| `OIDC_*` | підключення до Keycloak (3.5) |
| `INTEGRATION_CLIENTS` | ключі вебхуків ЄДЕБО, HR, ERP, Деканату, ЕДО (3.6) |
| `E2EE_SERVER_NAME` | ім'я сервера в ідентифікаторах шифрування; **не змінюйте після запуску** |
| `PKI_CA_*`, `PKI_PUBLIC_URL`, `VERIFY_CODE_SECRET` | ЦСК і QR-перевірка підписів; зміна `VERIFY_CODE_SECRET` робить недійсними надруковані QR |
| `QES_GATEWAY_*` | шлюз ІІТ «Користувач ЦСК» для КЕП (порожньо — КЕП вимкнено) |
| `LIVEKIT_*` | дзвінки (3.7) |
| `TRUST_INTAKE_SECRET` | анонімні звернення до служб довіри (порожньо — вимкнено) |
| `MINOR_LINK_HOSTS` | додаткові сайти, посилання на які дозволені неповнолітнім |
| `OUTBOX_*`, `SCHEDULE_LINK_HOSTS`, `ADMISSIONS_*` | боти (Деканат, ЕДО, розклад, консультант приймальної комісії) |

### 3.5. Keycloak (SSO) і двофакторна автентифікація

Месенджер не створює облікових записів і не має власних паролів. Людина може
увійти, лише якщо вона вже є в базі з синхронізації HR або ЄДЕБО і має
обліковий запис у Keycloak з тією ж електронною поштою.

1. Створіть реалм `puet` і підключіть AD / LDAP (User Federation). Для зразка
   є демо-реалм `infra/keycloak/puet-realm.json`. Не імпортуйте його в робочий
   Keycloak: у ньому тестові люди й відомий секрет.
2. Створіть клієнт `puet-pulse`:
   - Client authentication: On; Standard flow: On; Direct access grants: Off;
   - PKCE: S256;
   - Valid redirect URI: `https://pulse.puet.edu.ua/api/auth/callback`;
   - Post logout redirect URI: `https://pulse.puet.edu.ua/*`;
   - Web origins: `https://pulse.puet.edu.ua`.
   Секрет клієнта вкажіть в `OIDC_CLIENT_SECRET`.
3. Додайте до клієнта маппер «Authentication Method Reference (AMR)» (ID
   token: On).
4. У потоці `browser` задайте кроку «Username Password Form» конфігурацію з
   `Authentication reference` = `pwd`, а кроку «OTP Form» — `otp` (max age
   36000). За цим значенням месенджер бачить, що людина ввела другий фактор.
5. Для ролей, яким потрібна двофакторна автентифікація (ректорат, директори
   інститутів, фінанси, кадри, служби довіри, адміністратори), додайте
   людям обов'язкову дію «Configure OTP». Найзручніше зробити це через групу.
   WebAuthn (апаратні ключі) також підтримується.
6. Налаштування в `pulse.env`:
   ```
   OIDC_ISSUER_URL=https://sso.puet.edu.ua/realms/puet
   OIDC_CLIENT_ID=puet-pulse
   OIDC_REDIRECT_URI=https://pulse.puet.edu.ua/api/auth/callback
   OIDC_POST_LOGOUT_REDIRECT_URI=https://pulse.puet.edu.ua/
   ```

Під час першого входу людину знаходять за поштою і прив'язують до її
облікового запису Keycloak. Якщо обліковий запис у Keycloak видалили й
створили заново, адміністратор бази має скинути цю прив'язку
(`users.oidc_subject`).

### 3.6. Синхронізація з ЄДЕБО, HR і ERP

Люди, групи, кафедри і навантаження потрапляють у месенджер лише через
підписані вебхуки. Кожна система отримує власний ключ у `INTEGRATION_CLIENTS`,
прив'язаний до одного тенанта і переліку дозволених типів даних.

| Вебхук | Звідки | Що передає |
|---|---|---|
| `POST /api/integrations/hr/staff` | кадрова система | працівники, посади, кафедри, ролі |
| `POST /api/integrations/edebo/students` | ЄДЕБО / Деканат | студенти, групи, гуртожитки |
| `POST /api/integrations/teaching-load` | ERP | навантаження семестру (курси і їхні канали) |
| `POST /api/integrations/offboarding` | HR / ЄДЕБО | звільнення, відрахування, випуск |
| `POST /api/integrations/deanery`, `/schedule`, `/edo` | Деканат, розклад, ЕДО | довідки, зміни розкладу, реєстрація документів |

Формат підпису: заголовок `X-PUET-Signature: t=<час>,v1=<HMAC-SHA256>` над
сирим тілом, заголовки `X-PUET-Client` і `Idempotency-Key`. Готовий приклад
відправника — `apps/api/scripts/demo-data.ts`. Схеми полів — 
`apps/api/src/integrations/schemas.ts`.

Звільнена або відрахована людина втрачає доступ одразу: усі сесії
завершуються, внутрішні сертифікати відкликаються, архіви зберігаються.

### 3.7. Дзвінки (LiveKit)

1. На окремому сервері встановіть LiveKit Server (https://docs.livekit.io).
   Візьміть за основу `infra/livekit/livekit.yaml`.
2. Відкрийте у файрволі UDP 50000–60000 і TCP 7881. Порт 7880 проксіюйте
   через nginx як `wss://meet.pulse.puet.edu.ua` з TLS.
3. Згенеруйте ключ і секрет (секрет від 32 символів). Вкажіть їх у LiveKit
   (`LIVEKIT_KEYS`) і в `pulse.env` (`LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`,
   `LIVEKIT_URL`, `LIVEKIT_PUBLIC_URL`).
4. Вебхук LiveKit: `https://pulse.puet.edu.ua/api/calls/livekit/webhook`.
5. Додайте адресу LiveKit у `connect-src` політики CSP в nginx.

Без цих налаштувань месенджер працює, лише кнопки дзвінків неактивні.

### 3.8. Резервні копії

| Що | Як | Як часто |
|---|---|---|
| PostgreSQL | `pg_dump -Fc` або pgBackRest з архівом WAL | щоночі повна копія, WAL безперервно |
| MinIO (файли) | `mc mirror` на окреме сховище; версіонування бакетів уже ввімкнено | щоночі |
| `/etc/puet` (налаштування, ЦСК, TLS) | зашифрована офлайн-копія | після кожної зміни |
| Keycloak | його база даних | щоночі |

Redis і ClamAV копіювати не потрібно. Зберігайте копії щонайменше 30 днів, в
іншому приміщенні й зашифрованими. Раз на квартал відновлюйте копію на
тестовому сервері й перевіряйте, що месенджер запускається, а журнал аудиту
проходить перевірку ланцюга.

Зверніть увагу: зміст наскрізно зашифрованих чатів сервер не може прочитати
й відновити. Люди зберігають ключі на своїх пристроях і в резервній копії
ключів під власною парольною фразою («Налаштування» → «Увімкнути резервну копію»).

### 3.9. Оновлення

```bash
cd /srv/puet-pulse/app && git pull && pnpm install --frozen-lockfile && pnpm build
PULSE_ENV_FILE=/etc/puet/pulse.env pnpm db:deploy
PULSE_ENV_FILE=/etc/puet/pulse.env pnpm db:seed   # додає нові дозволи, безпечно повторювати
sudo systemctl restart puet-pulse-api
```

Перед оновленням зробіть резервну копію бази.

### 3.10. Моніторинг і безпека

- `GET /api/health` для моніторингу (Zabbix, Uptime Kuma).
- Журнал аудиту можна забирати в SIEM: `GET /api/admin/tenants/:tenantId/audit`.
- Журнали API не містять текстів повідомлень, токенів і телефонів. Зберігайте
  їх не довше, ніж вимагає політика університету.
- Перед запуском для всіх замовте незалежний тест на проникнення.

### 3.11. Пілот і запуск

| Етап | Тривалість | Хто | Мета |
|---|---|---|---|
| 0. Стенд | 1 тиждень | IT-центр | сервери, TLS, Keycloak, тестова синхронізація з копії HR і ЄДЕБО |
| 1. Технічний пілот | 2 тижні | IT-центр, 10–20 людей | сценарії з розділу 2, резервне копіювання й відновлення, дзвінки |
| 2. Пілот підрозділу | 4 тижні | 1 кафедра, 2–3 академічні групи, Канцелярія, омбудсмен | реальне листування, підписи, погодження; збір відгуків |
| 3. Інститут | 4–6 тижнів | 1 ННІ з усіма групами | навантаження, «Тихі години», боти Деканату й розкладу |
| 4. Університет | за графіком | усі ННІ, потім ліцей і коледжі | поетапне підключення тенантів |

Перед етапом 2:

- погодьте з відповідальним за захист персональних даних склад даних, що
  синхронізуються, і строки зберігання;
- затвердьте Регламент ЕДО ПУЕТ з урахуванням статусу УЕП внутрішніх
  підписів (КЕП — лише через сертифікований шлюз ІІТ);
- проведіть короткий інструктаж для старост, кураторів і секретарів кафедр за
  [USER_GUIDE.md](USER_GUIDE.md);
- призначте чергового адміністратора і канал зв'язку для повідомлень про
  проблеми.

Ліцей ПУЕТ (неповнолітні) підключайте останнім, після перевірки фільтрів
контенту на пілоті.

### 3.12. Що ще не перевірено з реальними системами

Ці частини перевірено автоматичними тестами з імітаціями, але не з
робочими системами університету. Перевірте їх на етапах 0–1:

- AD / LDAP-федерація Keycloak (демо-вхід із TOTP перевірено на Keycloak 26);
- вебхуки ЄДЕБО, HR, ERP, Деканату, розкладу, ЕДО (формат готовий, потрібні
  адаптери на боці цих систем);
- шлюз КЕП ІІТ (EUSignCP);
- LiveKit під навантаженням;
- MinIO з KES/HSM;
- інсталятори десктопної версії й підпис коду.
